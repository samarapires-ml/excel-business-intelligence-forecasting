# DAX KPI Engine

## Overview

This stage builds the analytical calculation layer for the **Nexora Commerce Business Intelligence model** using DAX in Power Pivot.

The KPI engine sits on top of the star schema created in the Data Model and provides reusable measures for revenue, orders, customers, products, quantity, operational quality, and time-based performance analysis.

---

## 1. Core DAX Concepts

### Measures vs. Calculated Columns

A **calculated column** evaluates logic row by row and stores a value for every row in the model.

A **measure** calculates an aggregated result dynamically based on the current filter context.

The transaction-level `Revenue` field was created earlier in Power Query because it is a row-level calculation.

Business KPIs such as Total Revenue, Core Orders, Average Order Value, and YoY Growth were implemented as DAX measures because they need to respond dynamically to filters.

### Filter Context

DAX measures automatically recalculate based on the active **filter context**.

Examples of filter context include:

- Year
- Country
- Product
- Customer
- Combinations of multiple dimensions

For example, `Core Sales Revenue` can calculate:

- Revenue across the entire dataset
- Revenue for a single year
- Revenue for a single country
- Revenue for a specific Country × Year combination
- Revenue for a selected product

The dimension tables filter the central fact table through the relationships in the star schema.

### CALCULATE

`CALCULATE()` evaluates an expression under a modified filter context.

It is one of the primary DAX functions used throughout this model.

```DAX
Core Sales Revenue :=
CALCULATE(
    SUM(fact_Transactions[Revenue]),
    fact_Transactions[AnalysisStatus] = "Core Sale"
)
```

This calculates revenue only for transaction lines classified as `Core Sale`.

### Measure Branching

Measure branching means building new measures from existing measures rather than repeatedly writing the underlying aggregation logic.

```DAX
Cancellation Revenue :=
CALCULATE(
    [Total Revenue],
    fact_Transactions[InvoiceType] = "Cancellation"
)
```

This improves readability, consistency, and maintainability.

## 2. Revenue Measures

### Total Revenue

```DAX
Total Revenue :=
SUM(fact_Transactions[Revenue])
```

Calculates net revenue across the current filter context.

### Core Sales Revenue

```DAX
Core Sales Revenue :=
CALCULATE(
    SUM(fact_Transactions[Revenue]),
    fact_Transactions[AnalysisStatus] = "Core Sale"
)
```

Calculates revenue generated by valid core-sale transaction lines.

### Non-Core Revenue

```DAX
Non-Core Revenue :=
CALCULATE(
    SUM(fact_Transactions[Revenue]),
    fact_Transactions[AnalysisStatus] = "Review / Non-Core"
)
```

Quantifies the revenue impact of transactions classified as non-core.

### Cancellation Revenue

```DAX
Cancellation Revenue :=
CALCULATE(
    [Total Revenue],
    fact_Transactions[InvoiceType] = "Cancellation"
)
```

Calculates revenue associated with cancellation invoices.

## 3. Transaction and Order Measures

### Transaction Lines

```DAX
Transaction Lines :=
COUNTROWS(fact_Transactions)
```

Counts transaction-line records.

The grain of `fact_Transactions` is **one product line within an invoice**, so transaction-line count is not equivalent to order count.

### Total Orders

```DAX
Total Orders :=
DISTINCTCOUNT(fact_Transactions[Invoice])
```

Counts distinct invoices in the current filter context.

### Core Orders

```DAX
Core Orders :=
CALCULATE(
    DISTINCTCOUNT(fact_Transactions[Invoice]),
    fact_Transactions[AnalysisStatus] = "Core Sale"
)
```

Counts distinct invoices containing core-sale activity.

---

## 4. Customer Measures

### Unique Customers

```DAX
Unique Customers :=
CALCULATE(
    DISTINCTCOUNT(fact_Transactions[Customer ID]),
    fact_Transactions[Customer ID] <> BLANK()
)
```

Counts identified customers while explicitly excluding blank Customer IDs.

This correction was introduced during model QA because `DISTINCTCOUNT()` can count a blank value as a distinct category.

**Validated total: 5,942 unique known customers**

This exactly matches the row count of `dim_Customer`.

### Revenue per Customer

```DAX
Revenue per Customer :=
DIVIDE(
    [Core Sales Revenue],
    [Unique Customers]
)
```

Measures average core-sales revenue per identified customer.

---

## 5. Order Value Measures

### Average Order Value

```DAX
Average Order Value :=
DIVIDE(
    [Core Sales Revenue],
    [Core Orders]
)
```

Measures average core-sales revenue per distinct core order.

`DIVIDE()` is preferred to the `/` operator because it safely handles divide-by-zero scenarios.

**Validated overall AOV: 493.96**

## 7. Time Intelligence

The `dim_Date` table was previously marked as the official Date Table in Power Pivot.

This enables DAX time-intelligence functions to operate against a continuous calendar.

### Previous Year Core Revenue

```DAX
Previous Year Core Revenue :=
CALCULATE(
    [Core Sales Revenue],
    SAMEPERIODLASTYEAR(dim_Date[Date])
)
```

Returns Core Sales Revenue for the corresponding prior-year period.

### YoY Revenue Change

```DAX
YoY Revenue Change :=
[Core Sales Revenue] - [Previous Year Core Revenue]
```

Calculates the absolute change in Core Sales Revenue versus the corresponding previous-year period.

### YoY Revenue Growth %

```DAX
YoY Revenue Growth % :=
DIVIDE(
    [YoY Revenue Change],
    [Previous Year Core Revenue]
)
```

Calculates year-over-year revenue growth relative to the previous-year period.

---

## 8. Revenue Quality Measure

### Core Revenue Share %

```DAX
Core Revenue Share % :=
DIVIDE(
    [Core Sales Revenue],
    [Total Revenue]
)
```

Measures Core Sales Revenue relative to overall net Revenue.

**Validated overall result: 106.25%**

A value above 100% is possible and is not automatically an error. `Total Revenue` includes negative cancellations and other non-core adjustments, while `Core Sales Revenue` excludes those negative effects.

## 10. Time Intelligence Caveats

The source dataset does **not** contain three complete calendar years.

Data coverage:

| Year | Coverage |
|---|---|
| 2009 | December 1 – December 31 |
| 2010 | Full calendar year |
| 2011 | January 1 – December 9 |

This has important analytical implications.

The calculated 2010 YoY growth of approximately **1,117.53%** is mathematically correct, but it compares a full year of 2010 against only one month of data from 2009. It therefore **must not be presented as true full-year business growth**.

Similarly, 2011 does not contain a complete calendar year.

For business trend analysis, matched-period and monthly comparisons should be preferred when periods do not have equivalent coverage.

Grand Total values for YoY measures should also be interpreted carefully. DAX evaluates a measure again under the Grand Total filter context rather than simply averaging or summing the visible yearly percentages.

## 12. QA Findings

The KPI validation process identified two important issues.

### Blank Customer IDs

The original `Unique Customers` measure used:

```DAX
DISTINCTCOUNT(fact_Transactions[Customer ID])
```

This returned **5,943** customers because the blank Customer ID was counted as an additional distinct value.

The measure was corrected to explicitly exclude blanks:

```DAX
Unique Customers :=
CALCULATE(
    DISTINCTCOUNT(fact_Transactions[Customer ID]),
    fact_Transactions[Customer ID] <> BLANK()
)
```

The corrected total of **5,942** matches `dim_Customer`.

### YoY Percentage Formatting

The YoY calculation was mathematically correct but was initially displayed as currency in the PivotTable.

The field was reformatted as a percentage with two decimal places.

This reinforced the distinction between:

- **Calculation logic** — what the measure computes
- **Display formatting** — how the result is presented

## 13. Key Lessons

1. **Measures respond dynamically to filter context.**
2. **`CALCULATE()` modifies the filter context in which an expression is evaluated.**
3. **Measures are preferable to calculated columns for reusable analytical KPIs.**
4. **`DISTINCTCOUNT()` can include blank values, so customer counts require validation.**
5. **`DIVIDE()` provides safer division than the `/` operator.**
6. **Measure branching improves model readability and maintainability.**
7. **A proper Date dimension enables DAX time intelligence.**
8. **Relationships allow dimension filters to propagate to the fact table.**
9. **DAX Grand Totals recalculate measures in the total context rather than simply aggregating visible cells.**
10. **A mathematically correct result is not necessarily a meaningful business comparison.**
11. **Formatting is separate from calculation logic and should be validated independently.**
12. **PivotTable QA is an important part of validating a semantic model before using it for business reporting.**
